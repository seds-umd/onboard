00 · Orientation

What you just joined

SATFAB is Satellite Component Fabrication, the project team inside SEDS@UMD that designs, builds and tests the parts a small satellite is made of. It has three subteams, Avionics, Power and Structures, plus systems design across the top. Avionics is the electronics and the software: circuit boards, the flight computer, sensors, the radio, and the firmware and gateware that run on them.

We are not starting from a blank page and we are not starting from a finished product. There is a payload built here and delivered to the Naval Academy, a balloon payload that flew past 100,000 feet in April, and a GPS receiver being built out of raw logic on an FPGA. This semester's main build, agreed at the 20 September meeting, is a new flight computer board that puts the processor, the radio and the motherboard onto one PCB with more sensors, plus an antenna and ground receiver so we can actually hear it. What each one actually is, and what state it is really in, is on the next page.

This club has lost its own knowledge before, and that is the one thing to know up front. People graduate, nothing is written down, and the next group starts over. Write things down as you go. It is the most valuable habit here.

01 · About two hours, and you only do it once

Set up your environment

This is the part that stops people, so it is written out in full. Follow it in order and do not skip ahead; each step assumes the one before it. If something fails, the fix is very likely written down here already. Tick items off as you go, and the bar at the top keeps your place in this browser.

We write flight firmware in C, built with CMake against the Raspberry Pi Pico SDK, and we work in a Unix shell: Ubuntu, WSL on Windows, or Terminal on a Mac. A Mac is a complete setup on its own; nothing here needs Windows or Linux. This is the same toolchain the delivered flight computer and the balloon payload are built with, so what you install today is what you will still be using in April.

Step 1 · A Linux shell

Pick your operating system. Everyone ends up at the same place: a Linux command line with a compiler in it.

Windows

You will install WSL, which runs a real Ubuntu inside Windows. Everything after this happens in the Ubuntu terminal, never in PowerShell or Command Prompt, with one exception noted in step 7.

  1. Install Ubuntu 22.04 from the Microsoft Store.
  2. Install Visual Studio Code, which is the editor we use with it.
  3. Turn the Windows features on. Search the Start menu for turn windows features on or off, tick Windows Subsystem for Linux and Virtual Machine Platform, and reboot if it asks.
  4. Open Ubuntu from the Start menu. It asks you to set a username and password. Nothing appears while you type the password. That is normal and not a bug. The password can be simple; it only guards this Linux environment, which sits behind your computer's own login.
  5. Make sure you are on WSL 2. In a Windows command prompt: wsl.exe --set-version Ubuntu-22.04 2. If it asks for a kernel update, get it from aka.ms/wsl2kernel and run the command again.
  6. In VS Code, install the WSL extension. Then open VS Code from inside your Ubuntu terminal by typing code . in the folder you want. The window that opens is editing Linux files with Linux tools, which is the whole point.
macOS

Your terminal is already Unix, so there is less to do. You need Apple's command line tools and Homebrew, which is the package manager we use for everything else.

  1. Open Terminal and run xcode-select --install, then accept the dialog. This takes a few minutes.
  2. Install Homebrew by pasting the command from its front page. It prints two or three extra commands at the end to add itself to your PATH. Run those, or nothing else will work.
  3. Install Visual Studio Code if you do not already have an editor you like.

Heads up The ARM compiler is the one part of this that is fiddlier on macOS than on Linux. Step 4 has the fix for the failure people actually hit. If you would rather not fight it at all, skip to using the lab machine.

No admin password, or a managed Mac Homebrew will not install without one. The Mac section of the sessions page has two routes that need none: Arm's toolchain tarball plus the CMake app in your own Applications folder, or VS Code with the Raspberry Pi Pico extension, which installs the SDK, compiler and picotool into ~/.pico-sdk by itself. The same section covers flashing (drag the .uf2 onto the RP2350 drive) and the serial port (screen /dev/cu.usbmodem* 115200, leave with ctrl-A, K, Y).

Linux

You are already done with this step. Go to step 2, and read the Linux and WSL instructions everywhere they appear.

Step 2 · Enough command line to get through the rest

If you have not used a terminal before, these six commands cover everything below.

ls                  # list the files here
pwd                 # print the full path of where you are
cd ~                # go to your home folder (~ is shorthand for it)
cd /path/to/dir     # go somewhere specific
mkdir new_dir       # make a folder
nano file.txt       # edit a file in the terminal; ctrl-O saves, ctrl-X exits

One habit worth having Press Tab to complete a file or folder name instead of typing it. It is faster and it stops typos, which are most of what goes wrong early on.

Step 3 · An SSH key, so git stops asking for passwords

An SSH key is a long secret that proves who you are to GitHub. You generate two halves. The public half you paste into GitHub and can share anywhere. The private half never leaves your computer, and you never need to open it.

# Use the email on your GitHub account. Press enter at every prompt
# to accept the defaults. A passphrase is optional.
ssh-keygen -t ed25519 -C "your_email@example.com"

# Print the PUBLIC half, and copy the whole line
cat ~/.ssh/id_ed25519.pub

Then go to github.com/settings/keys, press New SSH key, give it a name that says which machine it is from such as Laptop WSL Ubuntu, leave the type as Authentication Key, and paste. The line you paste starts with ssh-ed25519 and ends with your email.

Tell git who you are, so your commits are attributed to you:

git config --global user.name "First Last"
git config --global user.email "your_email@example.com"

Check it worked:

ssh -T git@github.com

You are looking for Hi [your username]! You've successfully authenticated, but GitHub does not provide shell access. That message is success, despite how it reads.

The one rule. The file ending in .pub is public and safe to paste anywhere. The file without that ending is your private key. It starts with -----BEGIN OPENSSH PRIVATE KEY-----, it should never be sent to anyone, posted anywhere, or copied off your machine, and no one here will ever ask you for it.

Step 4 · The compiler and build tools

Linux and WSL
sudo apt update
sudo apt install python3 git tar build-essential cmake \
                 gcc-arm-none-eabi libnewlib-arm-none-eabi

What these are build-essential is the compiler for your own machine, used by the unit tests. gcc-arm-none-eabi is the compiler that targets the ARM chip on the Pico. cmake turns a project into something buildable.

macOS
brew install cmake git
brew install --cask gcc-arm-embedded

If the compiler install fails, save the exact error and run which arm-none-eabi-gcc and arm-none-eabi-gcc --version. Ask for help before removing an existing course toolchain. The tarball or VS Code routes below avoid changing that installation.

No Homebrew at all? Take the tarball or VS Code route in the Mac section of the sessions page; both work without an admin password.

Step 5 · The Pico SDK

Same on macOS, Linux and WSL. This puts the SDK in ~/pico and tells your shell where to find it.

mkdir ~/pico
cd ~/pico

git clone https://github.com/raspberrypi/pico-sdk.git
cd pico-sdk
git submodule update --init          # pulls in TinyUSB and friends; not optional
cd ..

echo "export PICO_SDK_PATH=~/pico/pico-sdk" >> ~/.bashrc
source ~/.bashrc
On macOS, or if your prompt says zsh, replace both mentions of ~/.bashrc with ~/.zshrc. To check which shell you are in, run echo $SHELL. Getting this wrong is the single most common reason the next step fails with PICO_SDK_PATH not set.

Step 6 · Prove it works

Build the blink example. This compiles nothing of ours, so a successful build verifies the compiler and SDK for the selected board. Flashing, USB serial and sensor wiring are separate checks.

cd ~/pico
git clone https://github.com/raspberrypi/pico-examples.git
cd pico-examples
cmake -S . -B build-pico2 -DPICO_BOARD=pico2
cmake --build build-pico2 --target blink -j4

The last line of output should be:

[100%] Built target blink

You now have build-pico2/blink/blink.uf2. The lab target is the non-wireless Pico 2. Use a new build directory when changing boards; do not reuse a CMake cache from another machine or board. That file is a program, and step 2 of the intro project puts it on a board.

If the CMake configure command fails with PICO_SDK_PATH not set, your shell has not picked up step 5. Close the terminal, open a new one, and run echo $PICO_SDK_PATH. It should print a path. If it prints nothing, the export line went into the wrong file, which is the zsh trap above.

Step 7 · Windows only, letting WSL see the board

WSL cannot see USB devices on its own. usbipd hands a device across from Windows. You can skip this until you actually have a Pico in your hand, and you do not need it for the drag-and-drop flashing method.

Install usbipd-win, then, in a Windows command prompt as administrator:

usbipd list                          # find the bus id, looks like 2-6

usbipd bind --busid 2-6              # once per device, ever
usbipd attach --wsl --busid 2-6      # every single time you plug it in

Then back in Ubuntu, check it arrived:

lsusb
ls /dev/serial/by-id

Why the serial port matters That long path under /dev/serial/by-id is how our Python tools talk to a board. You will paste it into commands later, so it is worth knowing it is there.

Optional · Use the lab machine instead

There is a computer in the Cypress workspace with this whole environment already on it. If you do not want to install anything, or your laptop is struggling, you can SSH in and work there. It is also how you test hardware that is physically in the lab while you are not.

The wiki page Remote Development has the full procedure. In short: generate your SSH key as in step 3, add the public half to the spreadsheet that page links, and ask someone with admin rights to add you.

Known problem On the Cypress wifi, SSH to GitHub is blocked, so git fails there even with a working key. The fix on that page is to authenticate over HTTPS with gh auth login instead. Worth knowing before you conclude your key is broken.

Optional · A debug probe

Dragging a file onto the board is fine to start. Once you are debugging something real you will want to single-step code on the chip, which needs OpenOCD and a Picoprobe. The build steps are on the wiki's software setup page. Leave this until you need it.

The pins you'll use

Numbers, not names. The label printed on the board (GP15) is the number you use in C (gpio_init(15)). The physical pin count (1 to 40) is a different thing and you will rarely need it.

3.3 volts, not 5. The Pico's pins are 3.3 V. The sensor runs on 3.3 V from the 3V3(OUT) pin. Never feed a pin 5 V from VBUS. That is the one way to kill the board in this project.

BOOTSEL is the small button. Hold it while plugging in the USB and the Pico shows up as a drive. Drag your compiled .uf2 onto it and the board reboots straight into your program. That is the whole flashing process.

The onboard LED next to the USB connector is what step 2 blinks. On the non-wireless Pico and Pico 2, the C SDK names it PICO_DEFAULT_LED_PIN (GP25). Wireless Pico W and Pico 2 W boards use the wireless chip for the LED and need the SDK's wireless LED example instead. Step 3 uses a separate LED on GP15.

  1. Make a pull request against a repository that doesn't matter

    Clone github_practiceorg access, branch, add your name to the text file, push, open a pull request. Get the mechanics wrong somewhere harmless before you touch flight code.

    cd ~
git clone git@github.com:seds-umd/github_practice.git
cd github_practice

git checkout -b add-your-name        # never work directly on main
# edit text.txt, add your name and the date
git add .
git commit -m "Add my name"
git push -u origin add-your-name
    The -u origin branch-name matters. It pushes your new branch as a new branch. A bare git push on a branch that was never published can put your changes somewhere you did not intend. Get into the habit now, while the repository is a toy.

    Then open the pull request on GitHub and ask someone to look at it. That is the whole loop, and it is the same loop for every real change we make.

    Why Every change here arrives as a pull request that another person reads. Nothing goes straight onto main, including from the leads.

  2. Put the blink example on a real board

    You already built blink.uf2 in setup step 6. Now flash it:

    1. Unplug the Pico.
    2. Hold the BOOTSEL button down and plug it in while holding.
    3. It appears as a USB drive called RP2350 on a Pico 2 (RPI-RP2 on an original Pico).
    4. Drag blink.uf2 onto that drive. The board reboots on its own and starts blinking.

    The code you just ran is five lines of real work:

    #include "pico/stdlib.h"

int main(void) {
    const uint LED = PICO_DEFAULT_LED_PIN;
    gpio_init(LED);
    gpio_set_dir(LED, GPIO_OUT);

    while (true) {
        gpio_put(LED, 1);
        sleep_ms(250);
        gpio_put(LED, 0);
        sleep_ms(250);
    }
}
    On a Pico W or Pico 2 W the LED is wired to the wireless chip rather than to a normal pin, so PICO_DEFAULT_LED_PIN does not exist and this will not compile. Build pico-examples/pico_w/wifi/blink instead, or borrow a plain Pico for this step.

    Why You have now compiled code on your computer and made it run on a separate chip in your hand. Everything else on this page is a more complicated version of that.

  3. Blink SOS in Morse, from a button

    Your first project of your own, rather than one of theirs. Three short, three long, three short, pause, repeat, but only while the button is held. Releasing it turns the external LED off within about 5 ms, even during a dash. A stable 20 ms press starts the sequence again.

    Make a folder next to pico-examples, with two files in it. First CMakeLists.txt:

    cmake_minimum_required(VERSION 3.13)

include($ENV{PICO_SDK_PATH}/external/pico_sdk_import.cmake)
project(sos C CXX ASM)
set(CMAKE_C_STANDARD 11)
pico_sdk_init()

add_executable(sos sos.c)
target_link_libraries(sos pico_stdlib)
pico_add_extra_outputs(sos)      # this is what produces sos.uf2

    Then sos.c:

    #include "pico/stdlib.h"

#define LED 15             // external LED in the diagram, through 330 ohms
#define BUTTON 14          // pushbutton to ground, active low
#define UNIT_MS 200
#define POLL_MS 5

// Check release at least every 5 ms, including during a dash or gap.
static bool wait_held(uint32_t ms) {
    while (ms > 0) {
        if (gpio_get(BUTTON)) return false;
        uint32_t tick = ms < POLL_MS ? ms : POLL_MS;
        sleep_ms(tick);
        ms -= tick;
    }
    return gpio_get(BUTTON) == 0;
}

static bool flash(uint32_t on_ms) {
    gpio_put(LED, 1);
    bool held = wait_held(on_ms);
    gpio_put(LED, 0);       // always off on cancellation
    return held;
}

static bool play_sos(void) {
    const char *sos[] = { "...", "---", "..." };
    for (int i = 0; i < 3; ++i) {
        for (const char *s = sos[i]; *s; ++s) {
            if (!flash(*s == '.' ? UNIT_MS : 3 * UNIT_MS)) return false;
            if (s[1] && !wait_held(UNIT_MS)) return false;
        }
        if (!wait_held((i == 2 ? 7 : 3) * UNIT_MS)) return false;
    }
    return true;
}

int main(void) {
    gpio_init(LED);
    gpio_set_dir(LED, GPIO_OUT);
    gpio_put(LED, 0);
    gpio_init(BUTTON);
    gpio_set_dir(BUTTON, GPIO_IN);
    gpio_pull_up(BUTTON);
    while (true) {
        // Require a stable press before starting; repeat while held.
        if (gpio_get(BUTTON) == 0 && wait_held(20)) play_sos();
        gpio_put(LED, 0);
        sleep_ms(POLL_MS);
    }
}

    From your SOS project folder, configure for Pico 2 and build. Flash build-pico2/sos.uf2:

    cmake -S . -B build-pico2 -DPICO_BOARD=pico2
cmake --build build-pico2 -j4

    Why Named constants instead of twenty copy-pasted sleeps, a loop over a pattern, and a function that does one thing. The button also introduces you to the fact that mechanical switches bounce, which you will meet properly later. What bouncing is and what to do about it.

  4. Talk to a sensor over I2C and write a small driver

    Four wires to the Adafruit LSM6DSOX breakout, which is an accelerometer and gyroscope. Find the chip on the bus, ask it what it is, switch the accelerometer on, and read acceleration out as real numbers.

    This standalone example uses GP4/GP5. The seds-umd/onboard repository used in the sessions guide uses GP0/GP1; follow the wiring for the program you actually build. These are different tutorial programs, not flight motherboard wiring.

    imu.c:

    #include <stdio.h>
#include "pico/stdlib.h"
#include "hardware/i2c.h"

#define I2C_PORT      i2c0
#define SDA_PIN       4
#define SCL_PIN       5
#define LSM_ADDR      0x6A     // LSM6DSOX, SA0 low
#define REG_WHO_AM_I  0x0F
#define REG_CTRL1_XL  0x10
#define REG_OUTX_L_A  0x28

static int reg_write(uint8_t reg, uint8_t val) {
    uint8_t buf[2] = { reg, val };
    return i2c_write_blocking(I2C_PORT, LSM_ADDR, buf, 2, false);
}

static int reg_read(uint8_t reg, uint8_t *dst, size_t len) {
    // true on the write keeps control of the bus for the read that follows
    int r = i2c_write_blocking(I2C_PORT, LSM_ADDR, &reg, 1, true);
    if (r != 1) return -1;
    return i2c_read_blocking(I2C_PORT, LSM_ADDR, dst, len, false);
}

int main(void) {
    stdio_init_all();
    while (!stdio_usb_connected()) sleep_ms(10); // open a USB terminal first

    i2c_init(I2C_PORT, 400 * 1000);
    gpio_set_function(SDA_PIN, GPIO_FUNC_I2C);
    gpio_set_function(SCL_PIN, GPIO_FUNC_I2C);
    gpio_pull_up(SDA_PIN);
    gpio_pull_up(SCL_PIN);

    uint8_t who = 0;
    if (reg_read(REG_WHO_AM_I, &who, 1) != 1 || who != 0x6c) {
        printf("IMU not found: WHO_AM_I=0x%02x; check wiring/address\n", who);
        return 1;
    }
    printf("WHO_AM_I = 0x%02x, expected 0x6c\n", who);

    if (reg_write(0x12, 0x44) != 2 || // CTRL3_C: BDU and address increment
        reg_write(REG_CTRL1_XL, 0x40) != 2) {
        printf("IMU configuration failed\n");
        return 1;
    } // Accelerometer on, 104 Hz, +/- 2 g

    while (true) {
        uint8_t raw[6];
        if (reg_read(REG_OUTX_L_A, raw, sizeof raw) != sizeof raw) {
            printf("IMU read failed; sample skipped\n");
            sleep_ms(200);
            continue;
        }

        int16_t x = (int16_t)((raw[1] << 8) | raw[0]);
        int16_t y = (int16_t)((raw[3] << 8) | raw[2]);
        int16_t z = (int16_t)((raw[5] << 8) | raw[4]);

        // 0.061 mg per count at +/- 2 g, converted to g
        printf("%.3f  %.3f  %.3f\n", x * 0.061f / 1000.0f,
                                      y * 0.061f / 1000.0f,
                                      z * 0.061f / 1000.0f);
        sleep_ms(200);
    }
}

    Add it to your CMakeLists.txt. Note the two extra lines, which send printf output over USB so you can read it on your laptop:

    add_executable(imu imu.c)
target_link_libraries(imu pico_stdlib hardware_i2c)
pico_enable_stdio_usb(imu 1)     # printf goes to USB serial
pico_enable_stdio_uart(imu 0)
pico_add_extra_outputs(imu)

    Flash it, then open the serial port to see the output. On Linux or WSL, install screen if needed and use screen /dev/ttyACM0 115200, on macOS screen /dev/tty.usbmodem* 115200. Tilt the board and watch which of the three numbers goes to about 1.0. That is gravity, and it is the first time the board tells you something about the physical world.

    Every constant in that file came out of the datasheet: the address, the identity register and the value it should answer with, the control register that turns the accelerometer on, where the output lives, and how many milli-g one count is worth. Finding those five things in a 150-page PDF is the actual skill.

    If the program reports IMU not found, the chip is not answering with the expected identity. Check the wiring against the diagram, check you have 3.3 V and not 5 V on VIN, and check you have SDA and SCL the right way round. If it prints 0x69, you have an LSM6DS33 board rather than an LSM6DSOX, which is a different sensor with a different identity byte.

    Why This is the first real embedded skill and it is most of what flight firmware is. The balloon payload does exactly this, to a multiplexer and a current monitor, several times a second, at 100,000 feet.

  5. Draw a board

    Come to the PCB and surface-mount soldering workshops, then design a two-layer board in KiCad that meets the club's criteria. Clone kicad-libraryorg access first so your symbols and footprints match everyone else's.

    It has to have

    • Two layers
    • Two mounting holes
    • Text on the copper layer
    • Components on both the top and the bottom
    • Two connectors, at least one a standard part such as a pin header or JST
    • A power input at 3.3 V, 5 V or 12 V. Bonus for two different rails on one board, from a converter or a second input
    • An integrated circuit that talks over a protocol such as SPI or UART
    • Vias
    • Everything inside the fab house's design rules, which you check before you route anything

    Ideas, if you want one handed to you

    • A small shield for the Pico that connects to a sensor of your choice, which you then program
    • An LED array that spells a word or makes a shape
    • A breakout for a linear or switching regulator
    • A breakout for thermistors and a multiplexer, which is a real thing the balloon payload needs
    • An audio amplifier board

    The flow, once you have a design in mind:

    1 · Schematic
    Draw the circuit. Symbols from kicad-library
    →
    2 · Footprints
    Give every symbol a physical part
    →
    3 · Layout
    Place parts, route copper, both sides
    →
    4 · DRC
    Design rule check against the fab's limits
    →
    5 · Gerbers
    Export the files a factory reads
    →
    6 · Order & solder
    Five boards for a few dollars, plus shipping. One to two weeks

    → Scroll the diagram sideways

    KiCad's own documentation has a getting-started tutorial that walks this with a small board, and the wiki has a KiCad page with our own conventions. Adafruit's soldering guide is the best written one if you want to read ahead of the workshop.

    Why After this you can contribute to a real board, and there is one waiting.

03 · Afterwards

What comes after
