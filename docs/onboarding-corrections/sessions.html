Avionics: the sessions

The first two avionics sessions, written down so you can do them at your own pace or catch up if you missed one. Session one gets you a shell that builds Pico firmware: Ubuntu, WSL on Windows, or Terminal on a Mac. Session two puts a Pico 2 and a motion sensor on a breadboard and reads it over I2C. After that you pick real work on the fall balloon payload.

This page is the short version of what happened in the room. Start here has the same setup in full, with the fixes for the ways it breaks, and the five-step intro project. Use that one when something on this page is not enough.

For whoever is running the session

Bring

  • A Pico 2 and a data cable per person, plus two spares.
  • Two LSM6DSOX breakouts, breadboards, jumper wires, two STEMMA QT cables, and STEMMA QT to male-jumper cables if the breakouts have no headers soldered.
  • One set wired and known good before anyone arrives.
  • This page on a screen, and the GitHub org page open for invites.

Order of play

  • 0:00 accounts, cables, Wi-Fi. Start the SDK clone first.
  • 0:10 session one. Talk while it downloads.
  • 0:50 session two. Wire, build, flash, read.
  • 1:20 hand out first pull requests. Tick the session sheet.

When it breaks, check in this order

  • The cable.
  • SDA and SCL swapped.
  • WSL cannot see USB (usbipd).
  • PICO_SDK_PATH in the wrong shell file.
  • A Mac without an admin password on the Homebrew route; send them to route B or C.

Every command on this page was run again on a MacBook on 13 October with pico-sdk 2.3.1, CMake 4.4 and Arm GCC 15.3. Both builds produced their .uf2.

00 · Before you come

Four things that take time

All of these have a lag on someone else's side, so start them now rather than the day you need them.

  • Most of our repositories are private, so links to them show a 404 until you are in the seds-umd organization. You get an email invite and you have to accept it. The two repositories the sessions use, obc-firmware and onboard, are public, so you can do everything below before the invite lands.

  • terplink.umd.edu, search for SEDS, request to join. This is what formally makes you a member.

  • Swipe access to the lab comes from a Canvas course, not a form. The link and QR code are in the Discord. Until it goes through, message the channel when you are outside and someone lets you in. Zarif's station is in the workshop, not the conference room.

  • The Pico 2 has a micro-USB port. Charge-only cables look identical and are the usual reason a board never shows up on a laptop. The lab is short on them, which is why Zarif asked people to bring their own.

  • Everything in session one happens in a Linux shell. On Windows that is WSL, and the download is the slow part. Install Ubuntu 22.04, open it once, set a username and password, and you are ready. macOS and Linux need nothing in advance except xcode-select --install on a Mac. If a Mac is the only computer you have, read the Mac section first: everything on this page runs on it, and there is a route that needs no admin password. The full walk-through, including the WSL 2 check, is on the start page.

00 · If your only computer is a Mac

Everything here runs on macOS

No Windows machine, no Ubuntu, no virtual machine. Apple silicon or Intel, both work. Open Terminal (Applications, Utilities), take one of the three routes below, then continue with session one. Every block on this page that differs on a Mac has a macOS version next to it.

  • xcode-select --install
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
brew install cmake git picotool
brew install --cask gcc-arm-embedded
arm-none-eabi-gcc --version

    The first line installs Apple's command line tools, which bring git and a C compiler for your own machine; click Install in the dialog and wait, and if it says they are already installed, good. The second line installs Homebrew if you do not have it and asks for your password. After the brew lines, open a new terminal window: the last command should print a version. Then go to session one, step 2.

  • xcode-select --install
mkdir -p ~/pico ~/Applications && cd ~/pico
# download the "macOS (Apple silicon) hosted ... arm-none-eabi" .tar.xz from Arm's page (Intel Macs: darwin-x86_64), then:
tar xf ~/Downloads/arm-gnu-toolchain-*-darwin-*-arm-none-eabi.tar.xz
echo 'export PATH="$HOME/pico/'"$(ls -d arm-gnu-toolchain-*-arm-none-eabi | head -1)"'/bin:$PATH"' >> ~/.zshrc
# open the CMake .dmg from cmake.org and drag CMake into the Applications folder in your home folder, then:
echo 'export PATH="$HOME/Applications/CMake.app/Contents/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc
arm-none-eabi-gcc --version && cmake --version

    Arm's download page has the compiler, about 150 MB, and cmake.org has CMake as a .dmg. Nothing here touches a system folder, so no password is needed. Both version commands should print something; then go to session one, step 2. picotool is not available on this route without Homebrew, and you do not need it: the drag-and-drop flashing in session two works without it.

  • Install VS Code, then the Raspberry Pi Pico extension from its Extensions panel. The extension downloads the SDK, the Arm compiler, CMake, Ninja and picotool into ~/.pico-sdk by itself and needs no password. Click the Pico icon in the left bar, New Project From Example, choose blink, board Pico 2, then Compile in the bottom bar; Run flashes a board that is plugged in. For session two, Import Project on the cloned onboard folder and set the board to Pico 2.

    This route keeps you out of the terminal, which is fine for the sessions. Plan on route A or B eventually: the flight firmware is built and reviewed as a plain CMake project from the command line.

  • ls /dev/cu.usbmodem*
screen /dev/cu.usbmodem* 115200

    Hold BOOTSEL, plug the Pico in, let go: a drive called RP2350 appears in the Finder sidebar. Drag the .uf2 onto it. The drive disappears on its own and macOS may complain that the disk was not ejected properly; that is normal. On route A, picotool load -f -x build-pico2/blink/blink.uf2 does the same without touching the button, and needs no sudo on a Mac.

    The serial port is /dev/cu.usbmodem followed by digits, and it only exists while your program is running, not in BOOTSEL mode. To leave screen, press ctrl-A, then K, then Y. Closing the window instead leaves the port held until you unplug the board.

  • KiCad, for the board files in bpp-fall2026-hw: the macOS download is a .dmg. Drag KiCad into Applications, or into the Applications folder in your home folder if you cannot write to the system one. The club's symbol and footprint libraries live in seds-umd/kicad-library; add them under Preferences, Manage Symbol Libraries and Manage Footprint Libraries. Vivado, for the FPGA lane, does not exist for macOS; that work happens on the lab PC in Cypress. A debug probe is not needed for anything on this page.

Route B was checked on a MacBook on 13 October with pico-sdk 2.3.1, CMake 4.4 and Arm GCC 15.3: blink and the onboard demo both built and flashed.

01 · Session one · 30 September

The terminal

What Zarif had everyone run, in order. By the end you can turn C source into a file a Pico will run. Each block is one paste.

  • Ubuntu / WSL
    sudo apt update && sudo apt upgrade
sudo apt install python3 git tar build-essential cmake gcc-arm-none-eabi libnewlib-arm-none-eabi
    macOS
    xcode-select --install
brew install cmake git
brew install --cask gcc-arm-embedded
    macOS, without an admin password
    mkdir -p ~/pico && cd ~/pico
# download the "macOS (Apple silicon) ... arm-none-eabi" .tar.xz from Arm's page, then:
tar xf arm-gnu-toolchain-*-darwin-arm64-arm-none-eabi.tar.xz
echo 'export PATH="$HOME/pico/'"$(ls -d arm-gnu-toolchain-*-arm-none-eabi | head -1)"'/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc
arm-none-eabi-gcc --version

    The Homebrew cask asks for an administrator password, which a managed or borrowed Mac may not have. Arm's own download needs none: unpack it under ~/pico and put its bin folder on your path. Intel Macs take the darwin-x86_64 file instead. Either way the last line should print a version.

    gcc-arm-none-eabi is the compiler that targets the ARM core on the Pico. build-essential is the compiler for your own machine, used by the unit tests. If the Mac cask fails, it is a clash with an older ARM toolchain; the fix is on the start page, step 4.

  • mkdir ~/pico
cd ~/pico
git clone https://github.com/raspberrypi/pico-sdk.git
cd pico-sdk
git submodule update --init
cd ..
echo export PICO_SDK_PATH=~/pico/pico-sdk >> ~/.bashrc
source ~/.bashrc

    The submodule step pulls in TinyUSB and the rest, and it is not optional. It is also the slow step on the Cypress wifi.

    On a Mac, or if your prompt says zsh, the last two lines are ~/.zshrc instead of ~/.bashrc. Run echo $SHELL if you are not sure. Getting this wrong is the single most common reason the next step fails with PICO_SDK_PATH not set.

  • cd ~/pico
git clone https://github.com/raspberrypi/pico-examples.git
cd pico-examples
cmake -S . -B build-pico2 -DPICO_BOARD=pico2
cmake --build build-pico2 --target blink -j4

    The last line of output should be [100%] Built target blink, and you now have build-pico2/blink/blink.uf2. That file is a program. Session two puts one like it on a board. -DPICO_BOARD=pico2 matters: the lab boards are Pico 2s, and a plain build targets the original Pico.

  • Ubuntu / WSL
    cd ~
sudo apt install -y cmake gcc g++ git libusb-1.0-0-dev libftdi1-dev
git clone https://github.com/raspberrypi/picotool.git
cd picotool
mkdir build
cd build
cmake ..
make -j$(nproc)
sudo make install
    macOS
    brew install picotool

    sudo apt install picotool does not find a package on Ubuntu 22.04, which is why Zarif had everyone build it from source. It needs PICO_SDK_PATH from the previous step. What picotool does: loads a program over USB, reboots the board, and tells you what is on it.

    WSL only: Windows does not hand USB devices to Linux on its own. For picotool and the serial port you need usbipd-win, described in step 7 on the start page. The drag-and-drop method in session two needs none of that.

  • cd ~
git clone https://github.com/seds-umd/obc-firmware.git

    This is the firmware on the payload we delivered to the Naval Academy: an RP2040 flight computer with a command handler, a scheduler, flash logging and a radio driver. You are not building it today. Read readme.md and src/main.c, and notice that it is the same C, CMake and Pico SDK you just installed. The fall balloon firmware starts from pieces of it.

If you are running the session. Start people on the SDK clone first and talk while it downloads. The apt line and the clones are the only steps that need internet. Expect two kinds of failure: a leftover line in somebody's ~/.bashrc from another course (one person hit a missing ROS setup script, which is harmless and is fixed by deleting the line) and PICO_SDK_PATH landing in the wrong shell file on a Mac.

02 · Session two · 7 October

The breadboard

A Pico 2, an Adafruit LSM6DSOX breakout (accelerometer and gyroscope), four wires, and a small program from Zarif's onboard repository that reads it ten times a second. The payload's sensors look exactly like this.

  • Four connections, and that is the whole rig.

    Laptop to Pico 2: the micro-USB data cable. The micro-USB end goes into the port on the Pico, the other end into your laptop, through a USB-C adapter if your laptop has no USB-A port. Power, flashing and the serial console all travel over this one cable.

    Pico 2 to breadboard: push the Pico into the breadboard so its two rows of pins straddle the trench down the middle, USB port facing the top edge. Every pin now has its own row of holes to plug wires into.

    Pico 2 to sensor: four jumper wires from the rows beside pins 1, 2, 3 and 36 to the breakout's SDA, SCL, GND and VIN pads, as in the diagram below. A bare breakout needs header pins soldered on first; the no-soldering alternative is a STEMMA QT cable with male jumper ends plugged into the breakout's socket (black GND, red V+, blue SDA, yellow SCL). Check which the lab kits have before people arrive.

    Sensor to second sensor: one STEMMA QT cable between their sockets. Nothing else to wire; they share the bus.

  • The program uses I2C bus 0 on GP0 and GP1. Pin numbers below are the physical count on the Pico 2, starting at the top left with the USB port facing up.

    Pico 2Physical pinLSM6DSOX breakoutWhat it is
    GP01SDAData
    GP12SCLClock
    3V3 (OUT)36VINPower. The breakout regulates it down itself, so VIN is correct
    GND3, or any GNDGNDGround. Use a pin marked GND

    The breakout answers at address 0x6A as shipped. The example on the start page uses GP4 and GP5 for the same job; both are fine, the code decides which pins are the bus. Never feed anything from VBUS (pin 40, 5 V). Keep this tutorial circuit at 3.3 V; follow the selected breakout documentation.

  • Before building: use onboard-main.patch from the corrected guide bundle. It was checked against upstream commit 01c49fb. Apply it once in a clean source checkout; if git apply --check fails, stop and compare your source rather than forcing it or discarding someone's changes. The bundle includes corrected source as an alternative.

    cd ~
git clone https://github.com/seds-umd/onboard.git
cd onboard
# Replace /path/to with the folder containing the corrected guide bundle.
git apply --check /path/to/onboard-main.patch
git apply /path/to/onboard-main.patch
cmake -S . -B build-local-pico2 -DPICO_BOARD=pico2
cmake --build build-local-pico2 -j4

    The repository contains another machine's generated build folder. Leave it alone and use the new build-local-pico2 directory above; CMake caches are not portable. Your output is build-local-pico2/pico_sensors.uf2. The repository selects Pico 2 and RP2350 ARM in CMakeLists.txt, so this guide targets a non-wireless Pico 2. Ask before adapting it for an original Pico or a wireless board.

  • With the button

    Unplug the Pico. Hold BOOTSEL, plug it in, let go. It appears as a USB drive called RP2350. Drag pico_sensors.uf2 onto it and the board reboots into your program.

    With picotool
    picotool load -f -x build-local-pico2/pico_sensors.uf2

    -f asks a board that is already running something to drop into bootloader mode over USB, and -x runs the new program straight away. On Linux you may need sudo the first time, or the udev rule from the picotool readme.

  • Ubuntu / WSL
    screen /dev/ttyACM0 115200
    macOS
    screen /dev/tty.usbmodem* 115200

    The program waits until a terminal connects before it does anything, so nothing is wrong if the LED stays quiet. Once you are in you get Pico 2 sensor demo: LSM6DSOX and then ten lines a second: three accelerations in g and three rotation rates in degrees per second. Hold the board flat and one axis reads about 1.00. Tilt it and that 1.00 moves to another axis. Twist it and the gyro numbers jump. To leave screen, press ctrl-A then K, then y.

    What you should see
    Pico 2 sensor demo: LSM6DSOX
IMU  A[g]   0.02  -0.01   1.00  G[dps]     0.3    -0.1     0.2
---
IMU  A[g]   0.03   0.00   0.99  G[dps]     0.1     0.2    -0.3
---

    Board flat on the desk: the third acceleration is about 1.00 g and the gyro numbers hover near zero. With the program exactly as published, the first acceleration has a known format-string error. Apply the supplied onboard-main.patch before treating the numbers as valid. The corrected version prints a sample only after a successful read.

  • The program has real rough edges, and fixing one is the shortest path to your first contribution. Branch, change, push, open a pull request against onboard, and ask in the channel for a look. Pick one:

    The format-string correction is supplied. onboard-main.patch changes %6C.2f to %6.2f, avoids repeated initialization on error, and skips failed reads. It also corrects the gyroscope full-scale register encodings so degrees-per-second scaling matches the selected range. It is a local patch, not a merged upstream change. For a student contribution, document your setup or add a demonstrated feature instead of duplicating this fix.

    Two sensors are wired up in code and switched off. The repository has drivers for the MMC5603 magnetometer (address 0x30) and the MPL3115A2 barometer (address 0x60), commented out in main.c. Chain one onto the same bus with a STEMMA QT cable, check its voltage, address and identity, handle initialization/read errors, then enable its block and print valid data next to the IMU's. Do not enable a driver for hardware you have not connected.

    There is no readme. Write the one you wish you had an hour ago: what the program does, how to wire it, how to build and flash it.

    Every constant came from a datasheet. Open include/imu.h and the LSM6DSOX datasheet side by side, find where the 0x6C identity byte and the 0x10 control register come from, and change the accelerometer range from 2 g to 16 g. Finding those lines in a 150-page PDF is the actual skill.

If you are running the session. Have one known-good Pico and sensor wired before people arrive. The first failure is almost always the cable, the second is SDA and SCL swapped, the third is a laptop that cannot see the board from WSL. The serial step is where people stall, because the program prints nothing until a terminal is attached; say that out loud before anyone plugs in.

03 · After the sessions

Where this goes

The fall balloon payload is being rebuilt as a proper board with new firmware, and most of the work is open. Here is what exists as of 13 October and where each piece starts. Repositories marked org access need the GitHub invite from the first section.

Schematic drawn · layout next

The motherboard

Zarif's schematic for the fall board, in bpp-fall2026-hw (org access): an RP2350A, the same chip as the Pico 2, with an LSM6DSO32 IMU, an MMC5633 magnetometer, an MS5607 barometer, two 16 MB flash chips, an 8-channel analog multiplexer for thermistors and panel voltages, I2C headers for a GPS and a real-time clock, a debug header, USB and a battery terminal. Eight analog inputs, six digital pins and one I2C bus are exposed. The layout starts the week of 13 October.

Start Clone it, open it in KiCad, and run the electrical rules check. Then read the RP2350 hardware design guide next to the schematic.

Scaffold · every file open

The firmware

bpp-fall26 (org access) is the firmware for that board. Right now it is a main.c that starts the watchdog and six empty files: the multiplexer reader, flash logging, the GPS driver, a position estimate, telemetry. The delivered obc-firmware has working versions of the multiplexer, flash and telemetry code to port from, and the bugs we found in April's data are known and written down on the work page.

Start Pick one empty file. The multiplexer reader is the smallest and the most useful, because the sensors you breadboarded hang off the same I2C bus the board will use.

Part chosen · driver needed

The GPS

A SparkFun NEO-M9N breakout plugs into the board's I2C header. It needs a driver that talks u-blox's UBX protocol over I2C, and it needs the airborne dynamic model switched on, because the default setting stops reporting a position near 12 km and the balloon goes past 30.

Start Read the u-blox M9 interface description, section on UBX-CFG-VALSET and the dynamic model, then the SparkFun library for how they drive it over I2C. The driver is gps.c in the firmware.

Board on hand · bring-up

The FPGA GPS receiver

Our own receiver in logic, which works in simulation and has not run on a board since 2024. An Arty S7-25 development board is arriving this month, so the design in gps-rtl can go back onto hardware.

Start Talk to Jaiden. Install Vivado if you have the disk space; the simulation side needs only Java 17, sbt, cocotb and Icarus.

Biggest gap · owner reading in

The radio and ground station

The payload talks through an OpenLST radio at about 437 MHz, and nobody on the team has yet heard it from the ground. The antenna and a receiver are being researched now, including a deployable antenna design borrowed from the Quetzal-1 CubeSat, which flew. Whoever operates the radio needs an amateur radio licence.

Start Ask in the channel who is on it and join them. openlst-software and the CC1110 datasheet are the reading.

04 · When it breaks

The failures people actually hit

  • -bash: /opt/ros/iron/setup.bash: No such file or directoryA line from an earlier course is still in your ~/.bashrc. It is harmless. To stop seeing it, nano ~/.bashrc, delete the line that mentions ros, ctrl-O, ctrl-X.
  • PICO_SDK_PATH not setYour shell has not picked up the export line. Close the terminal, open a new one, run echo $PICO_SDK_PATH. If it prints nothing, the line went into .bashrc on a machine that uses zsh, or the other way round.
  • CMake Error: The source directory does not match the source used to generate cacheYou ran cmake inside a build folder that came from another computer. Leave that cache alone and configure a new directory, for example cmake -S . -B build-local-pico2 -DPICO_BOARD=pico2, from the source root.
  • The board never shows up, or shows up and vanishesThe cable. Charge-only micro-USB cables are indistinguishable from data cables by eye. Try another one before anything else. On WSL, the board also has to be attached with usbipd before Linux can see it.
  • picotool: No accessible RP2350 devices in BOOTSEL mode were foundAdd -f so it reboots the board for you, or hold BOOTSEL while plugging in. On Linux, run it with sudo once or install the udev rule.
  • LSM6DSOX init failedIf the message says the identity byte was wrong, the chip answered but it is not the expected part. If it said 0x69 you have an LSM6DS33 breakout, which is a different part. If the init fails with a bus error instead, check SDA and SCL are not swapped and that VIN has 3.3 V.
  • screen: cannot open /dev/ttyACM0The port appears only after the program starts, and only once the board is plugged in normally, not in BOOTSEL mode. ls /dev/ttyACM* to see what is there. On a Mac the name starts with /dev/tty.usbmodem.
  • Mac: zsh: command not found: brewHomebrew is not installed, or the terminal was opened before it was. Open a new terminal; if it still fails, take route B or C in the Mac section.
  • Mac: "arm-none-eabi-gcc" cannot be opened because the developer cannot be verified, or just "killed"Gatekeeper quarantined the downloaded toolchain. Run xattr -dr com.apple.quarantine ~/pico/arm-gnu-toolchain-* once and try again.
  • Mac: screen says the port is busy, or shows nothing after a reflashAn earlier screen is still attached to it. Quit it with ctrl-A, K, Y, or close every terminal tab that opened the port, then unplug and replug the board.
  • Nothing printsThe program is waiting for you. It does not start until a terminal is attached, by design, so you never miss the first lines.
  • The first acceleration column is nonsenseVerify that the supplied onboard-main.patch was applied before building. Rebuild the corrected source and flash that output; do not trust the malformed upstream column.
